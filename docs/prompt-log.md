# 核心 Prompt 记录

> 记录引导 AI 开发的最核心 Prompt，覆盖 SDD / DDD / TDD / E2E 四个阶段。
> 每段附「当时意图 / 遇到的挑战 / 如何引导修正」。

---

## Prompt 01 ｜【SDD 阶段】数据建模与 API 契约

**原始 Prompt：**

> 你是资深全栈架构师。为「AI 圆桌讨论 Web App」做数据建模，**先不要写任何代码**。
> 1. 输出完整 ER 图（mermaid `erDiagram`），每张表说明存在的理由；
> 2. 明确指出哪张表是唯一事实来源，其余表如何由它派生；
> 3. 用表格输出 REST API 契约（方法、路径、请求体、响应体、错误码）；
> 4. 单独列出 SSE 端点的事件类型与 payload 结构；
> 5. 所有表必须支持多讨论物理隔离。
> 约束：数据库 SQLite；模型 API Key 只能在服务端读取。

**执行说明：**
- **意图**：先冻结数据结构，避免写代码阶段反复改表。
- **挑战**：AI 第一版把 `messages` 当成了权威表，导致"断线重连如何补发"无法回答。
- **修正**：明确要求"`events` 为唯一权威、其余为投影"，并强制补上 `seq` 单调递增与 `Last-Event-ID` 补发方案后才通过。

## Prompt 02 ｜【DDD 阶段】前端组件与页面生成

**原始 Prompt：**

> 基于 `docs/api.md` 与三栏布局要求，输出前端组件树（缩进列表）+ 每个组件的 props 定义，**先不要写实现**。
> 布局要求：桌面端三栏（嘉宾小窗 / transcript / 共识分歧），**每个区域在自身容器内独立滚动**，不能整页滚动；宽度 < 1024px 时降级为单列。
> 状态来源必须说明：哪些数据来自初始 `GET /detail`，哪些来自 SSE 事件，如何避免重复渲染。

**执行说明：**
- **意图**：先定组件边界和状态归属，防止把 SSE 逻辑散落在各组件里。
- **挑战**：AI 初版把整页设为 `overflow-y: auto`，超宽屏下 transcript 被拉得极长；且未处理"详情接口 + SSE 回放"导致的重复消息。
- **修正**：补充"各栏 `overflow-y:auto` + `min-height:0`"的硬性要求；并要求对消息按 `id`、共识按 `content` 去重后再渲染。

## Prompt 03 ｜【TDD 阶段】核心逻辑的测试用例与业务实现

**原始 Prompt：**

> 先只为 `validatePlan` 写 Vitest 测试，**不要写实现**。覆盖以下规则，每条一个 `it`：
> 1. 合法输出返回空错误数组；
> 2. 发言人数 > 2 报错；
> 3. `participantId` 不在候选名单报错；
> 4. 与上一轮发言者完全相同报错；
> 5. `mustRebutt` 为 true 但无人 `rebut` 报错；
> 6. 单条内容 < 20 字报错；
> 7. 同一轮出现重复发言人报错。
> 断言用 `errors.some(e => e.includes(...))`，不比对完整文案。

**执行说明：**
- **意图**：把 PRD 里的"调度硬性规则表"逐条翻译成可执行断言，形成文档与代码的一一对应。
- **挑战**：AI 初版把校验直接写在路由里，依赖 `req/res`，无法脱离 HTTP 测试。
- **修正**：要求先把 `validatePlan(plan, ctx)` 抽成纯函数（只依赖入参），测试才能在 4ms 内跑完；实测 7 条用例总耗时 309ms，其中测试本身仅占 2%。

## Prompt 04 ｜【E2E 阶段】系统级端到端测试与质量闭环

**原始 Prompt：**

> 用 Playwright 写 E2E，覆盖两条主链路：
> A. 首页：拦截 `GET /api/discussions` 返回固定列表，断言标题、两条议题、`已结束`/`未开始` 状态标签、`N 人参与` 文案。
> B. 直播页：拦截 `GET /api/discussions/:id` 返回一份已结束的完整 fixture，断言三栏标题、嘉宾小窗、transcript 内容、`反驳` 标签、共识与分歧条目、总结三块。
> 要求：全部走 `page.route` 网络 mock，不依赖真实模型与后端；断言遇到多处匹配时使用 `.first()`。

**执行说明：**
- **意图**：让测试可在无网络、无 API Key 的环境下稳定复现，作为"质量闭环"的自动化关卡。
- **挑战**：直接打真实模型时，单次讨论 5~30 秒且内容不确定，测试必然 flaky；且 `EventSource` 的流式响应难以在 Playwright 中 mock。
- **修正**：把 E2E 的边界定义为"渲染契约"——只验证给定数据下 UI 结构正确；实时性由人工验收清单兜底。文案重复导致 strict mode 冲突时，统一加 `.first()`。

## Prompt 05 ｜【修复阶段】SSE 不推送与状态机脱节

**原始 Prompt：**

> 现象：直播页左上角一直显示「第 0 轮」，内容不实时更新，刷新后才发现已结束。
> 已知：直接打开 `http://localhost:3001/api/discussions/:id/stream` 能看到 `round_start` 递增。
> 请分析这是渲染问题还是传输问题，给出最小修复方案，并说明为什么。

**执行说明：**
- **意图**：让 AI 先做归因（客户端 / 传输 / 服务端），再动代码，避免盲改。
- **挑战**：AI 第一反应是修改 `round` 的初始值与渲染逻辑，但根因是 **Vite 开发代理缓冲了 SSE 长连接**，事件根本没到浏览器。
- **修正**：把 `EventSource` 改为直连 `http://localhost:3001`（后端已开启 CORS），并在 hook 中加入 `onopen`/`onerror`/`round_start` 日志用于自证。同时发现 seed 中一条 `status='running'` 但无进程的"僵尸数据"，记录为待改进项。
